# ADR-0001: Site and engine stack

- Status: accepted (Phase 0)
- Date: 2026-09-23

## Context

The repository must publish a bilingual (EN canonical, KO mirror) learning
site with search, render every equation from a single source of truth with a
build that *fails* on bad math, host interactive calculators and a
time-domain simulator in the browser, and be deployable as static files to
GitHub Pages. A Python side must independently verify every equation.

## Decision

- **Astro + Starlight** for the site. Starlight provides locale routing
  (`src/content/docs/en`, `src/content/docs/ko`), fallback to English with an
  "untranslated" notice, sidebar generation and **Pagefind** static search
  out of the box, and Astro's islands let tool pages ship JavaScript while
  documentation pages ship none. Output is fully static.
- **MDX** content with custom components (`<Eq>`, later `<Cite>`, `<Quiz>`,
  `<Mission>`, `<ResourceList>`).
- **KaTeX at build time, strict.** Equations are rendered to HTML during the
  build (no client-side math JavaScript). `<Eq>` calls
  `katex.renderToString(…, { throwOnError: true, strict: 'error' })`, and
  inline `$…$` in MDX goes through `remark-math` + `rehype-katex` wrapped by
  `src/math/rehype-katex-strict.ts`, which turns rehype-katex's warnings into
  build errors. Macros are allowed only from `src/math/macros.ts`.
- **Astro 7 Markdown processor: `unified()`** from `@astrojs/markdown-remark`
  instead of the default native Sätteri processor, because `remark-math` and
  `rehype-katex` are unified plugins. Starlight supports both processors.
- **React islands + Plotly** (`plotly.js-dist-min`, dynamically imported,
  `client:only`) for tools, so Plotly never runs during SSR and is only
  downloaded on tool pages.
- **TypeScript engine `packages/pe-core`** (npm workspace), tested with
  **Vitest**. Evaluators are hand-written and checked against vectors
  generated by the Python side.
- **Python `python/pe_core`** with **sympy** (pinned, because generated LaTeX
  depends on the printer) for parsing, derivations, LaTeX and test-vector
  generation, tested with **pytest**.
- **GitHub Actions**: `ci.yml` (tests, generator diff-check, lints, strict
  build, link check with lychee) and `pages.yml` (build and deploy).

## Alternatives considered

- *Docusaurus*: good i18n, but heavier React runtime on every page and
  client-side math by default.
- *MkDocs Material*: excellent docs tooling, but interactive tools would live
  in a separate JavaScript build.
- *VitePress*: Vue-based; fine, but the tools are more natural as React
  islands with Plotly.
- *MathJax*: slower, and its error handling is less suited to a fail-the-build
  policy than KaTeX's `throwOnError`.

## Consequences

- LaTeX must stay within KaTeX's supported command set; the vitest suite
  renders every generated formula with the same strict options, so problems
  surface before the site build.
- Content authors never type equation LaTeX; they edit `equations.yaml` and
  run the generator.
- The Pages site lives under the `/switching_converter_study/` base path;
  internal links in content are written relative to the current page.
